SLIDE 3 — PROBLEM STATEMENT (60 seconds)
--------------------------------------------------------------------------------
What to say:

"Why do we need this?

Today:
- ELK detects issues, but it cannot fix them.
- Engineers jump between logs, dashboards, and tickets.
- Same problems keep repeating — DB pool full, API errors, login spikes.
- Fixing one incident often takes 45 to 90 minutes.
- There is no clean audit trail from detection to resolution.

Business impact:
- Transfers/payments fail → customers suffer and SLA penalties rise.
- Engineers waste time on repeat work → higher OpEx.
- Security spikes are slow to handle → fraud risk.
- Regulators want proof of every action, and manual reports take days.

So the problem is not monitoring.
The problem is the gap between seeing an issue and fixing it safely."

EASY EXAMPLES TO USE WHILE PRESENTING
================================================================================

Use these if someone asks "Give one example" or if you have extra time.


--------------------------------------------------------------------------------
EXAMPLE 1 — TRANSFER FAILURE (MAIN EXAMPLE)
--------------------------------------------------------------------------------
Situation:
Customers try to transfer money, but transfers start failing.

What ELK sees:
- Transfer API error rate high (5xx)
- Database connection pool almost full (98%)

What TAS does:
1. Detects the alert
2. Diagnoses: "DB connection pool is exhausted"
3. Creates ServiceNow SEV-2 ticket for Banking SRE
4. Shows recommended fix in portal: increase pool + restart pods
5. Engineer clicks Approve
6. Fix runs automatically
7. Transfers start working again
8. Ticket closes and audit is saved

Time:
- Before: ~75 minutes
- After: ~12 minutes


--------------------------------------------------------------------------------
EXAMPLE 2 — LOGIN / SECURITY SPIKE
--------------------------------------------------------------------------------
Situation:
Suddenly many failed login attempts appear — maybe an attack or bad bot traffic.

What ELK sees:
- Failed login rate is 10x normal

What TAS does:
1. Detects the spike
2. Marks it as a security-related incident
3. Creates ServiceNow ticket for SecOps
4. Sends Teams notification
5. Shows plain-English summary in portal
6. Engineer reviews and takes next action (or approves guided response)

Why this matters:
Security issues need speed. Manual ticket creation wastes critical minutes.


--------------------------------------------------------------------------------
EXAMPLE 3 — SERVICE UNAVAILABLE
--------------------------------------------------------------------------------
Situation:
Login service or one banking API goes down. Users cannot access the app.

What ELK sees:
- Health check fails / service unavailable alert

What TAS does:
1. Detects service down
2. Creates SEV-1 ServiceNow ticket
3. Recommends restart of the service pod
4. Engineer clicks Approve
5. Service restarts on Azure
6. Service recovers, ticket updates, audit saved

Why this matters:
This is a clear, low-complexity, high-impact automation case.

================================================================================
LIKELY QUESTIONS + SHORT ANSWERS
================================================================================

Q1: Are you replacing ELK or ServiceNow?
A: No. We use both. We only add the automation layer between them.

Q2: Is this fully automatic?
A: Not for high-risk actions. Engineer approval is required for fixes like
   pod restart or DB pool scaling.

Q3: Is customer data safe?
A: Yes. We do not log PII, account numbers, passwords, OTPs, or balances.

Q4: Why only 3 problems in Phase 1?
A: To deliver real value fast, prove the model, then extend safely in Phase 2.

Q5: How long to deliver?
A: About 12 weeks for Phase 1 end-to-end demo.

Q6: Who will use the UI?
A: NOC, SRE, and SecOps teams. Only 3 screens — list, detail, approve.
